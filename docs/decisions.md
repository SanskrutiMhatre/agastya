## S1. Temporary password scheme (`username@year`)

**Decision (user, Phase 1 change 3).** When an account is created or a password is reset or reissued, the server sets a temporary password of the form `<username>@<year>`, where the year is the current year at issue time, for example `ravi@2026`. This value does not have to meet the normal password policy; only temporary passwords get this exemption.

**This scheme is predictable.** Anyone who knows a username and the year can work out the temporary password. Between issue and first use, the account can be taken over by whoever signs in first. The limits below are the mitigation, and they are the reason this scheme is acceptable:

1. **First sign-in only.** A successful sign-in with the temporary password marks it used (`temp_password_used_at`). It cannot be used again, even if no new password was chosen.
2. **Immediate forced change.** That sign-in lands behind the onboarding or forced-change gate. `evaluate()` refuses everything else until a new, policy-compliant password is set.
3. **24-hour expiry.** `temp_password_expires_at` is issued time plus 24 hours. After that the temporary password is refused even if unused.
4. **Reissue.** The creating Project Manager (for their Authors) or the Software Administrator can reissue it. Reissuing resets the 24-hour clock, clears the used flag and revokes every session.
5. **Shown once.** It is returned to the creator in the single create, reset or approve response. It is never stored in plain text, never written to logs and never written to the audit log (the audit sanitiser drops any key resembling `password`, and no route passes it in metadata). `security-regression.js` checks the captured server log for every temporary password it was issued.
6. **Rate limit still applies.** The 10-per-15-minutes limit per username + IP covers temporary-password sign-ins exactly as it covers normal ones.
7. **Short gated session** (A4): the session that sign-in creates lasts at most 30 minutes.

Residual risk: within the 24-hour window, and before the real user signs in, someone who knows the username can sign in first. The real user would then find the temporary password already used and ask for a reissue, which revokes the other session. Distributing the temporary password out of band and signing in promptly keeps this window small. A random temporary password would remove the risk; that is a one-function change in `server/auth/policy.js` (`tempPasswordFor`) if the decision is revisited.

The bootstrap administrator's password (A7) is not a `username@year` temporary password. It comes from the environment, must meet the policy and is behind a forced change.

## Content lock (before checkpoint 2c)

| # | Decision | Notes |
|---|---|---|
| L1 | **While a publication request is pending, its frozen sources are read-only for every Author on the project** (the submitter and co-authors alike): the publication module, the data modules it places, their graphics and BREX, and `project.json`. Writes are refused with **423 `LOCKED_PENDING_APPROVAL`** and a message naming the submitter, the manager and the date: on module save and delete, the publication XML save, builder save and import, a frozen graphic's upload, and the wording settings. Modules the publication does not place, new modules and new graphics stay editable. | User, after 2b. Graphics, BREX and `project.json` are included because otherwise replacing one would make the request stale and so lift the lock. |
| L2 | **The lock is derived, not stored**: the locked files of a project are the union of the files in its pending requests' snapshot manifests (`server/content/locks.js`). So a data module placed in two publications is locked by a pending request on either, and the lock lifts the moment a request stops being pending: withdrawn, rejected, changes requested, approved or stale. | One publication per project today; the two-publication case is unit-tested. |
| L3 | **The Software Administrator is exempt** from the lock; their content edits are the Phase 4 override (written reason) and mark the request stale. Until then their writes are refused as `OVERRIDE_REQUIRED`, never as locked. | PROMPT.md |
| L4 | **Shown, not only enforced:** a "Locked: pending approval" banner and read-only state in the data module editor, the publication builder, the XML view and the wording settings; a Locked badge (and no Delete) in the module list; a note on the pending request. The lock is never revealed to someone who cannot see the project (they get 404). | |
